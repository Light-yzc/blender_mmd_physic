# 历史烘焙说明（5.36 已暂停）

以下说明仅为历史记录，当前版本不提供这些入口，隔离烘焙工具也已停止执行。

## 区间烘焙、删除与单组停用

| 操作 | 作用范围与结果 |
| --- | --- |
| Ruri「区间烘焙」 | 当前骨架中全部启用的 Ruri 配置，写入独立动作 |
| Ruri「Delete Bake」 | 按骨架记录恢复原动作，并删除可安全删除的本轮烘焙动作 |
| Ruri「恢复实时」 | 按骨架恢复原动作与实时模拟，保留烘焙动作 |
| Wiggle「区间烘焙」 | 按当前骨架的可用 Wiggle 骨骼烘焙 |
| Wiggle「取消烘焙」 | 按骨架记录恢复烘焙前动作，保留烘焙动作 |
| 「取消本组物理」 | 仅停用当前组实时 Ruri / Wiggle / 旧碰撞，恢复已记录的 MMD 跟随 |

**单组停用不会移除已经写入动画动作的物理关键帧。** 它不切换整副骨架的动作，也不会要求先取消其他组的烘焙。已有关键帧仍会播放。

只有当前插件记录过的烘焙才能自动恢复。旧版覆盖写入、缺失备份的动作不能凭空还原。列表里的「移除」或「清空」也不能代替停用已经应用的物理。

## 一键烘焙 Blender 原生布料

入口：**骨骼链面板最下方 → 烘焙**，默认折叠。在「烘焙对象」选择场景布料、Ruri 当前骨架或 Wiggle 当前骨架，三个对象共用区间和「正常烘焙／内存受限烘焙」两个按钮。Ruri / Wiggle 原有的分散烘焙入口已合并到这里，复位、删除及恢复实时也随对象切换显示。骨架模式处理该骨架全部启用配置，不是只处理当前分组。

1. 将「烘焙对象」设为「场景布料（含上游骨架）」；设置起止帧，或点「使用场景区间」。
2. 设置预模拟帧数，默认 30 帧。
3. 保持「先烘焙上游 Ruri／Wiggle」开启。
4. 选择「正常烘焙」或「内存受限烘焙」。正常烘焙在当前 Blender 执行；内存受限烘焙支持 Linux Ruri / Wiggle 和节点布料，需要保存工程后运行，结果另存新副本。
5. 正常烘焙完成后保存 `.blend`；内存受限烘焙完成后打开日志中记录的新副本。两种路径都需保留工程旁的缓存目录。节点布料明确写入磁盘；传统 Cloth 使用磁盘点缓存。

例如：动画 600–700 帧、预模拟 30 帧，会把骨骼和布料的烘焙计算区间设为 570–700 帧，场景动画区间保持原样。

执行顺序：

```text
布料依赖的骨架物理（例如胸部、头发）
    ↓
作为碰撞体或代理的上游布料
    ↓
依赖上游结果的衣物、裙摆与饰品
```

批处理以**场景**为范围，上游骨骼按**骨架**烘焙启用配置，不是只烘焙当前胸部分组。被手动停用的 Cloth 修改器会跳过；隐藏代理会临时显示用于烘焙，结束后恢复隐藏和选择状态。

同一依赖层中的节点布料逐对象烘焙。采样骨骼时暂停下游布料，烘焙布料时暂时暂停尚未轮到的下游对象，结束或中止后恢复修改器显示状态，以减少无用的实时模拟缓存。

按 `Esc` 中止。已经完成的阶段保留，具体顺序与结果写入工程内的文本 **「原生布料烘焙记录」**。

「删除场景布料烘焙」只删除启用布料对象的原生缓存，保留 Ruri / Wiggle 骨骼烘焙动作。

### Bake 时的内存保护

Blender 5.2 的原生节点 Bake 会保留已经计算的帧状态，**写磁盘也不等于逐帧释放内存**。5.32 的存储改动不足以限制单个长 Bake 的内存。

5.35 在面板底部统一烘焙入口，选择烘焙对象后使用两个按钮：「正常烘焙」在当前进程执行，没有内存硬上限；「内存受限烘焙」使用独立进程：场景模式先处理上游骨架，再按依赖顺序每个对象启动一次 Blender；Ruri / Wiggle 模式只处理所选骨架，不要求存在布料。一个对象在完整区间内连续模拟，完成后保存进度并退出进程，再处理下一个对象。不会把时间区间截断为独立模拟。

默认工作进程上限 8 GiB；每次启动前还会将它下调至「当前可用物理内存减 1.5 GiB」以内，且禁用该工作单元的交换空间。单个任务超过上限会被终止，队列停止；这保证有上限，不保证任意复杂对象都能在上限内完成。主界面原有内存不会因此被清理；建议使用已经导出磁盘缓存的工程副本。

内存受限模式没有降低求解质量、子步、网格精度或跳过帧；每个对象仍连续模拟整个区间。额外的进程启动和工程读写可能降低整体速度。尚未做两条路径的结果对比，不能承诺逐位一致；超限会停止，而不会自动降质量继续。

需要先保存工程与设置。烘焙结果写入同目录 `原名-limited-bake-随机标识.blend` 和它的缓存目录，原工程、原磁盘缓存保留。`Esc` 请求中止；日志显示停止位置。中止或超限后，失败阶段的缓存可能不完整，工具不会自动继续。

也可从命令行运行：

```bash
python3 tools/bake_limited.py /path/to/project.blend --blender /path/to/blender --memory-limit 8G
```

默认使用插件里保存的区间与预模拟设置。隔离模式支持 Ruri / Wiggle 单独烘焙；场景模式只处理可识别的**几何节点布料**，遇到传统 Cloth 会明确停止；「正常烘焙」支持原有传统 Cloth 路径，但没有内存硬上限。隔离 Bake 完整流程尚未实测。

### 长序列与内存

5.32 起使用磁盘缓存，避免把整段节点模拟打包进 `.blend`。**这不等于 Blender 播放时只保留一帧内存**：5.2 的节点模拟会保留已加载的帧状态，长序列仍可能增加内存占用。旧工程中的打包缓存也不会因为更新插件自动转为磁盘缓存。

仓库提供 Linux 分段渲染工具，每段使用独立 Blender 进程，并以用户 systemd 限制工作进程的内存，默认 8 GB、不使用交换空间。默认每 32 帧退出进程，释放该段累计的节点与渲染缓存。超限只会终止该工作单元，队列随即停止，不自动重试。

先保存好物理烘焙和图像序列输出设置，然后运行：

```bash
python3 tools/render_chunks.py /path/to/project.blend \
  --blender /path/to/blender \
  --start 600 --end 3240 --chunk-size 32 --memory-limit 8G
```

工具沿用工程内的渲染器、相机、分辨率和输出位置，不改写工程。需要 PNG / EXR / JPEG 等图像序列，不能直接分段输出视频；已有同名输出可能被覆盖。物理应事先烘焙，工具不补算或修改缓存区间。根据机器可用内存调整上限；单帧本身就超过上限时，需要降低渲染开销或增大上限。普通界面的「渲染动画」不会自动变成分段渲染，也没有这个进程内存上限。

内存改动已做代码检查；磁盘缓存转换与工程重新打开完成过实际诊断。新的批处理与分段渲染尚未运行完整长序列，不能保证已消除所有渲染崩溃。

### 依赖循环

碰撞与变形不能形成循环。例如：

```text
上层裙摆 Proxy → 碰撞集合 → 上层裙摆网格 → Surface Deform → 同一个 Proxy
```

批处理会在执行前报出循环对象，先修正碰撞集合再重新执行。可采用单向关系：身体驱动上层裙摆，上层裙摆再作为下层裙摆的碰撞来源。
